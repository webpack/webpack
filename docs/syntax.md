# Syntax modules: parser, printer and minifier

<!-- Moved out of AGENTS.md so it loads only when needed; AGENTS.md keeps a pointer here. -->

Read this before touching the CSS, HTML or JavaScript parser, printer or minifier.

## Shared by every language

`lib/css/`, `lib/html/` and `lib/javascript/` each hold the same five pieces:

- `syntax.js` — a facade reaching `syntax-parser.js` (reads) and `syntax-printer.js` (writes) through getters, so a walk that never prints never loads the printer. It is neither parser nor printer.
- Every export of a `syntax.js` facade, and of the JavaScript parser's `{ path: true }` taps (`PathTaps`, `nodeOfPath`, the `…ByPath` helpers), is experimental: its JSDoc carries `@experimental <where it is exposed>; unstable API`, and so does each public name added to it.
- `syntax-parser.js` / `syntax-printer.js` — algorithm only; every lookup table they read is in `data.js` — except generator-written regions such as the HTML entity table (`// #region html entities` in `lib/html/syntax-parser.js`) — generated by `tooling/generate-css-data.js`, `generate-html-data.js` or `generate-js-data.js` (see "Do not touch" in `AGENTS.md`).
- A minify entry the default minimizer dispatches to: `cssMinify.js`, `htmlMinify.js`, `jsMinify.js` — and `xmlMinify.js` for `.svg` and `.xml`, under `experiments.futureDefaults` or an `optimization.minimizeOptions.xml` object.
- A spec-conformance suite (`yarn test:css-parsing`, `test:html5lib`, `test:xmlconf`, `test:test262`) and the invariants and ecosystem comparison in [tooling/COMPARE_TOOLS.md](../tooling/COMPARE_TOOLS.md).

## Shared names

The three parsers store a tree the same way, so the same concept has the same name in every `syntax-*.js`: a reader who knows one language reads the others. A new name for a shared concept goes in this table and replaces every other language's spelling in the same change; a concept only one grammar has (HTML's sibling links and attribute columns, CSS's `_aux0`/`_aux1`, JavaScript's `_slots`/`_bases`) keeps its own name.

| Concept                                               | Name                                                                                                                                                                  |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| node type, offsets and flags columns                  | `_types`, `_starts`, `_ends`, `_flags`                                                                                                                                |
| nodes written, column capacity, growth                | `_nodeCount`, `_nodeCapacity`, `growNodeColumns` (JavaScript reads the capacity off `_types.length` and grows in `SyntaxTree#_growNodeColumns`)                       |
| a node's list of children, as a span                  | `_listStarts`, `_listLengths` into `_listItems`, filled up to `_listItemTop`                                                                                          |
| the empty column a released one shares                | `EMPTY_U8`, `EMPTY_U16`, `EMPTY_I32`, one per typed-array kind                                                                                                        |
| the path object and its class                         | `A`, `<Language>SyntaxPath`                                                                                                                                           |
| regrow hint and peak from a parse                     | `_nodeGrowHint`, `_listItemGrowHint`, `_nodePeak`, `_listItemPeak` (CSS; JavaScript keeps the hints as `nodeGrowHint`, `listItemGrowHint`; HTML regrows without them) |
| capacity above which columns are freed                | `SHRINK_CAPACITY`                                                                                                                                                     |
| reset before a parse, free after it                   | `resetColumns`, `releaseColumns` (CSS resets in `setupParse`; JavaScript's pooled tree has the public `SyntaxTree#reset` and `#release`)                              |
| write a node                                          | `makeNode` (`makeLeaf`/`makeContainer` in CSS, the public `SyntaxTree#addNode` in JavaScript), `makeAttr`                                                             |
| line and column converter                             | `_locConverter`, a `LocConverter` given its language's line terminators (JavaScript's `getLineInfo` keeps acorn's answer inside a CRLF)                               |
| the caller's `parseError` and the reporter calling it | `_parseError`, `reportParseError` (a module variable `parseError` in JavaScript, beside `parseErrorsSeen`)                                                            |
| walk position                                         | `_walkNode`, `_walkIndex`, `_walkParent` (HTML reads index and parent off its sibling and parent links; JavaScript keeps the enclosing nodes as `_walkParents`)       |
| walk control and visitors                             | `_walkSkipped`, `_walkStopped`, `_walkVisitors`, `_walkHalted`                                                                                                        |
| character-class table                                 | `CHAR_CLASS`                                                                                                                                                          |
| the input the walk reads, cleared on release          | `S._input` (CSS keeps the caller's string before NUL replacement as `_originalInput`)                                                                                 |

No module-level name carries a `_` (`nodeGrowHint`, `SHRINK_CAPACITY`, `CHAR_CLASS`, `S`); a field keeps it (`_types`, `S._walkNode`), and so does the key of an export only tests reach (`module.exports._S = S`). The walk state is a field of one object, `S`: the tree in CSS and HTML, `JavascriptWalkState` in JavaScript, so `S._walkNode` reads the same in every language.

## The node path

Every visitor and node printer receives one argument, the language's `path`: `webpack.css.syntax`, `webpack.html.syntax` and `webpack.javascript.syntax` hand over an object with the same members under the same names, named after ESTree where ESTree has the concept. `NodePath<TNode>` in `lib/util/SourceProcessor.js` is that contract, and `SourceProcessor` takes only a path satisfying it, so a missing or misnamed member fails `lint:types`.

```js
const links = [];
new SourceProcessor()
	.use([NodeType.Element], (path) => {
		const href = path.fieldNamed(Field.attributes, "href");
		if (href !== 0) links.push([path.value(href), path.loc(href)]);
	})
	.process(source);
```

`Field`, `Flag` and `Part` are exported beside `NodeType` and named with the spec's word: CSS Syntax's for CSS (a rule's `declarations` and `rules` read as empty on a block big enough to stream, so read those from the walk), the DOM's for HTML. A `Flag` is a bit of the node's flags column (`important`, an element's namespace and `selfClosing`) or read off a token's text (CSS's type flags).

```js
path.fieldNamed(Field.declarations, "color"); // CSS: the declaration, 0 if none
path.flag(Flag.important); // CSS
path.field(0, Field.content); // HTML: a <template>'s fragment
for (let i = 0, n = path.fieldCount(Field.attributes); i < n; i++) {
	names.push(path.name(path.field(i, Field.attributes))); // HTML: nodes the shared members read
}
path.rangeOf(Part.name); // where the name is written, null without one
```

The types follow the same tables: a visitor registered for some node types gets a path whose `field`, `fieldCount`, `fieldNamed`, `flag`, `rangeOf`, `textOf` and `within` accept only the parts those types have, and an item read from a field is typed as its node type. So `use([NodeType.Comment], (path) => path.fieldCount(Field.attributes))` fails to type-check, as does reading attributes off an attribute; a node of unknown type (`parent`, `child(i)`) takes any part.

No language has a member of its own, the writes below aside: what one grammar has is a row in its `NodeType`, `Field`, `Flag` or `Part` table, read through the members above, so a new language adds tables, not methods.

HTML's `Part.content` runs to where the content ends when the end tag was left out, and an element the parser inserted has no `name`, tag or `content` range.

`skipChildren()` still fires the node's `exit`, since the printer prints a node there. After `stop()` neither the current node's remaining visitors nor any pending `exit` fire. A print still writes the whole output, and a walk-only parse ends there: CSS once the top-level rule it was called in closes, HTML at once (HTML visits nothing before about 49k nodes have parsed, so stopping early in a big document still pays for that much parsing).

A run's state reaches every visitor as `path.state`, so visitors keep no closure of their own. Its type is the processor's: `new SourceProcessor<{ count: number }>()` in TypeScript, or a `@type` annotation in JSDoc, types `path.state` in every visitor and makes `process` take only that shape:

```js
/** @type {import("webpack").css.syntax.SourceProcessor<{ count: number }>} */
const processor = new SourceProcessor();
processor
	.use([NodeType.Ident], (path) => path.state.count++)
	.process(source, { state: { count: 0 } });
```

One visitor serves several node types through an array, resolved once in `use()` so the walk sees the same per-type slots: `processor.use([NodeType.Text, NodeType.Comment], visitor)`.

Conventions every language keeps, and a new member follows:

- **A node is an integer id**, valid until the next parse; `0` is no node, and an HTML attribute's id is negative. The path is one object rebound before each callback; read it during the callback, never keep it.
- **A parse entry point returns ids too**, read through the exported path `A` until the next parse (`parseHtml`, CSS's `parseA*`, JavaScript's `parseProgram`), and takes a `parseError(input, code, start, end, severity)` option reporting each parse error of the tokenizer and of the parser or tree construction: `"error"` where end of input cuts a token or rule short, or where a JavaScript one stops the parse, and `"warning"` otherwise; without the option, HTML and CSS leave a `"warning"` unreported, and `parseProgram` throws its first error, recoverable or not, as acorn does (with the option it returns `undefined` for an `"error"`). No spec names them all, so HTML's tree-construction errors take html5lib-python's names, JavaScript's take Babel's `reasonCode` kebab-cased (read off probes by `tooling/generate-js-data.js`), and CSS's are webpack's own.
- **The node is the last argument and optional**, defaulting to the current one: `path.range()`, `path.range(other)`, `path.child(0)`.
- **A node has at most one `name` and one `value`; every other part is a `Field`, a `Flag` or a `Part`** (its position, and its text when it has more than the name and value), so the generic members cover any grammar instead of one method per part.
- **`name` and `value` are what the language's spec defines**, decoded as ESTree's `Identifier.name` and `Literal.value` are: escapes and character references resolved, a number as a number, a comment's text without its delimiters. **`source` is exactly the input**, so the spelling as written is `source(path.startOf(Part.name), path.endOf(Part.name))`. A node without a name or value answers `""`, a missing part `null`.
- **Positions come as numbers and as ranges**, like acorn's `start`/`end` and `range`: `start`, `end`, `startOf` and `endOf` allocate nothing, so `CssParser` and `HtmlParser` read every position through them; `range`, `rangeOf` and `loc` (`[line, column, endLine, endColumn]`) are a fresh array per call.
- **Walk children one way everywhere**: `for (let i = 0, c = path.child(0); c !== 0; c = path.child(++i))`. HTML keeps where the last `child` read stopped per parent, so this takes one step per child even with nested loops.
- **Nothing is stored for a read.** A member reads the columns the parser already fills or derives its answer when called: HTML counts `index` along the sibling links and makes `loc`'s converter on its first call in a parse. The walk writes no more than its position, so a read nobody makes costs nothing.
- **Writes act on the current node and only while printing.** `replace(text)` and `remove()` take effect when the node prints after its visitors, which still run its printer for what it records; on a walk that prints nothing, or on a comment, which prints from the token stream, they do nothing, and a rule whose block is large enough to stream prints as written. In CSS, what holds a replaced node prints the text its children printed as, without the minifier's rewrites, which read fields the replacement no longer matches; the rest of the sheet minifies as before. HTML streams most elements to the output before their `exit`, so an element replaced there prints as written; one replaced from its `enter` composes at once instead. JavaScript has no writes: its printer decides parentheses, spacing and semicolons from the original node and mangles the names around it, which a replacement's text would not match.
- **Reads go through the path, and webpack's own plugins read through it.** `CssParser` and `HtmlParser` use the members above and nothing else from a node, so what they do a plugin can; only the printers keep raw readers of their own (`_rawName`, `_attributeList`, …).

## Generated tables

**In the generator, derive — don't type out.** Read tables from published datasets (`mdn-data`, `color-name`, `@webref/idl`) whenever derivable, _including by analyzing a grammar rather than listing names_: the value-definition syntax says which properties take an `<integer>`, so that set is computed. An existing `SUPPLEMENT` table counts as a source too — cosine at each eighth turn is sine two eighths along, and each inverse trig table is its forward one read back.

**Per-construct behavior is a table too.** Where the minifier differs per name (each math function; next, properties or at-rules), the per-name part is a descriptor in the generator and the shared part an engine in `syntax-printer.js` keyed by it. `MATH_FUNCTION_FOLD` is the example: it says how each function's arguments are read, which arithmetic runs and what unit results carry, so the printer implements none and names no function. The arithmetic is emitted alongside and bound by reference, not name, so an undefined name fails generation instead of folding nothing. A new function is one line; one whose arithmetic exists needs nothing else. A test must drive every descriptor (one input per entry) so a wrong-but-existing binding fails instead of silently declining. Hand-listing names into `SUPPLEMENT` is the last resort, each entry stating why it can't be derived (spec prose, an equivalence between spellings, a judgement no dataset states) — hand lists go stale unnoticed when specs move; derived ones turn a spec change into a reviewable diff.

### What each generated table holds

- `lib/css/data.js` — every table the CSS minifier looks names up in, plus the arithmetic its math-function descriptors bind to: from `mdn-data` + `color-name` (box shorthands, color-argument and math functions, named colors) and the generator's `SUPPLEMENT` of spec-prose tables and math primitives, by `tooling/generate-css-data.js` — which also holds the value-definition-syntax parser those grammars are read with, and runs generation only as the entry point so its tests can require it.
- `lib/html/data.js` — every table the HTML parser and minifier look names up in: reflected-attribute tables from webref's HTML IDL (`@webref/idl`, `@webref/elements`) plus the generator's `SUPPLEMENT` and `PARSER_TABLES` of §13.2 tree-construction vocabulary, by `tooling/generate-html-data.js` — which also emits the `// #region html entities` block in `lib/html/syntax-parser.js` from the vendored `tooling/html-entities.json` (WHATWG's named character references).
- `lib/javascript/data.js` — the JS parser's and printer's Unicode tables: run-length identifier ranges the tokenizer decodes at its first non-ASCII code point, and per-edition `\p{...}` property names (reached only for a pattern the engine rejected), which `tooling/generate-js-data.js` reads from the pinned acorn devDependency — bumping it moves them; plus the Unicode 8.0 identifier ranges the printer writes unescaped (so older engines read its output), read from terser's own frozen tables; and `NodeType`, `Field`, `Flag`, `Part` and `NODE_FIELDS`, each ESTree node type's number, fields and their slots in a `SyntaxTree`, typed out in the generator.
- `lib/javascript/parse-error-codes.js` — each parse error message with its code, Babel's `reasonCode` kebab-cased, read off probes both parsers read; in its own module, loaded by the first error `parseProgram` reports, so a parse reporting none never loads it.
- `lib/javascript/syntax-printer-data.js` — the tables only the printer reads, in their own module so a build that parses without minifying through the printer never loads them: the native-object tables of pure globals, calls, methods and static properties the compressor reads (`NATIVE_*`, built only when `nativeObjectTables()` is called, so loading the module allocates none), each name with its `unsafe` / `builtins_ecma >= N` conditions in terser's order, parsed with acorn out of terser's `lib/compress/native-objects.js`. Plus the keyword, reserved-word and operator-precedence tables the printer names tokens by (`parserTables()`), parsed out of terser's `lib/parse.js`, and the DOM property names property mangling keeps (`domProperties()`), out of its `tools/domprops.js`. Plus the built-ins `improve` evaluates on literals (`foldedBuiltIns()`): `tooling/generate-js-data.js` places every member `@mdn/browser-compat-data` lists of `Math`, `Number`, `String`, `Array` and the global functions in `FOLDED_BUILT_INS`, `FOLDED_CONSTANTS` or, with the reason, `UNFOLDED_BUILT_INS`, and fails when a bump lists one in neither, or a folded one is missing, misplaced, or newer in Node than `engines.node` (folding it would tie the output to the build's Node). Plus the constructors `improve` calls without `new`, `CONSTRUCTED_WHEN_CALLED`, each one the spec has construct the same when called. Plus the built-ins `improve` drops (`pureBuiltIns()`): every global and standard static member BCD dates to `engines.node`, less the ones `IMPURE_BUILT_INS` and `UNREAD_BUILT_INS` name with the reason (`eval`, a promise combinator that may reject, `Intl`, …); a call is dropped only where running it at build time on its literal arguments does not throw.

## CSS

- `syntax.js` publishes the parser, the printer and `SourceProcessor` only — read a former re-export off `parser` or `printer`.

## HTML

- `syntax.js` mirrors `css`, publishing the parser, the printer and `SourceProcessor` only. `syntax-parser.js` holds the tokenizer, §13.2 tree construction and the entity table.

## XML

- `parseHtml(…, { xml: true })` reads XML 1.0 through `tokenizeXml` and its own token handlers (`XML_PARSE_CALLBACKS`), so the HTML handlers carry no XML branch on their per-token path. Names are case-sensitive, there are no insertion modes, and the internal DTD subset's entities and attribute defaults are applied — an entity holding markup is tokenized in place and printed as its reference, under a nesting limit and an expansion budget.
- The printer then writes XML, never HTML, and offers `renderEmbeddedSource` only an SVG or XHTML element's `<style>` (of no type or `text/css`) and `style=""` — the namespaces where they are CSS. Like an HTML `<style>`, the sheet is offered with `as: "embedded-stylesheet"`: it is read in the document's encoding, so `cssMinify` declares no `@charset` for it. `xmlMinify.js` hands those to `builtinEmbeddedRenderer` with the CSS options and browsers a `.css` asset gets.
- `optimization.minimizeOptions.xml.comments` decides which comments survive, as `minimize.html.comments` does, through the printer's `transforms.comments`. Its default, `"some"`, keeps an XML legal notice (a comment opening with `!` or annotated `@license` or `@preserve`), as svgo does; `false` drops that too. An SVG `data:` URL follows it as well.
- An SVG or XHTML `<script>` holding JavaScript and every event handler attribute are offered to `renderEmbeddedSource` as HTML offers them: a script as `"script"` or `"module"`, a handler as `"event-handler"`, written back only where shorter. A script that loads a file through `href` keeps its text. `xmlMinify` lists them in `getEmbeddedTypes` and asks the minimizer plugin's renderer first, so the JavaScript minifier answers them with its own `comments`, as the CSS minifier answers a stylesheet with `minimize.css.comments`; what it declines `builtinEmbeddedRenderer` answers.
- `optimization.minimizeOptions.xml.removeMetadata` removes SVG `metadata` subtrees; `removeEditorData` removes elements and attributes in known editor namespaces within SVG. Both default to `false`, preserve `title`, `desc`, namespace declarations and subtrees containing IDs, and use the HTML printer's `xml: true` mode (`removeSvgMetadata` / `removeSvgEditorData` on `SourceProcessor`). DTD content models and unread DTD declarations disable subtree removal; declared editor attributes stay. Metadata can carry licensing or application data; editor data may be needed to edit the image. Editor data also stays where a stylesheet has an attribute selector or is unread, since a selector can match an editor attribute.
- `optimization.minimizeOptions.xml.removeUnusedNamespaces` drops unused prefixed namespace declarations within SVG, preserving default namespaces, local bindings and prefixes referenced in names or content (`removeUnusedSvgNamespaces` on `SourceProcessor`). `removeEmptyAttributes` reuses the HTML printer to drop empty SVG `class`, `id` and `style` attributes, including styles the CSS renderer makes empty, unless the DTD declares them. It also drops any other unprefixed SVG attribute whose value is empty, since an empty presentation or geometry value is invalid and reads as absent; it keeps `xmlns`, `href`, `target`, `download`, `crossorigin`, `lang`, the conditional `requiredExtensions`, `requiredFeatures` and `systemLanguage` (which an empty value fails), `aria-*`, `data-*` and event handlers, and everything on animation elements. `removeUnusedNamespaces` defaults to `true`, since no name uses the declarations it drops, and `removeEmptyAttributes` to `false`, because selectors and scripts can observe attribute presence. External DTDs and DTD parameter entities keep these attributes and namespace declarations because unread declarations can supply defaults.
- `optimization.minimizeOptions.xml.collapseWhitespace` removes whitespace-only text in known SVG containers, under `xml:space` too since that lays out text alone, preserving text and foreign content; a stylesheet that mentions `empty`, imports another or is unread keeps it, since `:empty` tells whitespace-only text from none. A page that inlines the SVG applies its own stylesheets, which the minimizer cannot read, so set `collapseWhitespace: false` where those select `:empty`. `shortenNumbers` removes redundant signs and zeros from known geometry and presentation attributes and compacts `viewBox`, point, text-position, filter-number and stroke-dash lists, without rounding or rewriting units, writing out only an integer's exponent where the result is at most 2^24, which a float32 holds exactly as Blink reads it, where shorter (`1e1` → `10`; `-1e-1` and `1.5e1` stay) (`shortenSvgNumbers` on `SourceProcessor`). In `points`, a sign separates coordinates as the points grammar reads it (`30.5-1`). Both default to `true`; numeric cleanup preserves DTD-declared attributes and is disabled for unread DTD declarations. Numeric and color cleanup also preserve attribute spellings when CSS contains attribute selectors or external stylesheets are unread.
- `shortenNumbers` also compacts SVG 1.1 transform lists, replacing exactly diagonal matrices with `translate` or `scale` where shorter and dropping redundant transform arguments: `translate(x 0)` → `translate(x)`, `scale(x x)` → `scale(x)` and `rotate(a 0 0)` → `rotate(a)`. `translate(x y) rotate(a) translate(-x -y)` becomes `rotate(a x y)`, which SVG defines as that list, and a sign separates arguments as the transform grammar reads it (`translate(-10-20)`). Equality is checked without arithmetic or rounding; zero exponents outside SVG’s finite float range stay written. Identity functions, including a zero `rotate` about any center (cos 0 and sin 0 are exact), are omitted when another transform remains; an all-identity list keeps one function so transform presence stays, and `cleanupStructure` drops it where presence cannot matter. Leading adjacent translations can fold within the exact eighth-unit bounds; leading adjacent scales fold only for powers of two with exact single-precision products. Other folds stay written because browser matrix and pixel values can change despite algebraic equivalence. Matrix aliases, folding and identity removal are disabled when local animation elements or CSS mention transforms. External stylesheet links, imports and XML stylesheet instructions preserve transform functions and path commands because the animation rules are unread. `optimization.minimizeOptions.xml.shortenPathData` compacts path numbers, repeated commands, axis-aligned lines, curves with default first controls and separators without rounding or changing segments, preserving implicit segments, subpath starts and arc flags (`shortenSvgPathData` on `SourceProcessor`). Curve shorthands also compare reflected controls within bounded exact eighths, preserving unsupported reflections and overflow cases. Absolute path commands also use shorter relative coordinates when every changed coordinate is an exact eighth within ±1,000,000; the differences fit exactly in single precision, with no rounding. Relative endpoints are tracked within the same bounds, preserving subpath starts and vertices. Inside a relative run a relative segment may cost two more characters, which compress away, and a relative source turns absolute only to save four; where those runs leave the data longer than written, each segment takes its shorter spelling instead. Other coordinate spellings, exponents and negative zero stay outside arithmetic cleanup. Zero-length absolute arcs remain absolute because Chromium otherwise changes marker orientation. A leading `M x y l` becomes `m x y` where no separator replaces the letter. In a document without a `marker` element, stylesheet, script or animation, a path without markers or `pathLength`, and without an ID on it or an ancestor, also drops a line back to its subpath start before `z`, and a move nothing draws from. Where it paints no stroke and hit-tests only its fill, it drops `z`, zero-length segments and last lines back to the start too, since a fill closes each subpath itself. A `url()` paint keeps a dropped move, which can shrink the box the paint measures. Without `precision`, data whose relative points a float32 renderer sums to other points than exact sums stays as written. Path cleanup is disabled when local animation attributes or CSS mention `d`, since interpolation requires matching commands. `shortenColors` offers opaque SVG 1.1 presentation colors to the same CSS renderer as inline styles, preserving paint servers and contextual colors (`shortenSvgColors` on `SourceProcessor`). `removeEmptyElements` reuses the shared printer option to drop empty SVG `g`, `defs`, `symbol`, `marker`, `pattern`, `mask` and `clipPath` containers with only namespace declarations, preserving other attributes, IDs, text and DTD defaults. `removeEmptyElements` defaults to `false` and the other two to `true`; all three preserve DTD-declared values and are disabled for unread DTD declarations.
- `optimization.minimizeOptions.xml.mergeDisjointPaths` (`mergeDisjointSvgPaths` on `SourceProcessor`), off by default, merges adjacent paths of any shape with the same attributes whose bounds, stroke included, do not overlap, as `removeOffCanvasPaths` bounds them. A path with an ID, `style`, `vector-effect`, marker, dash, `pathLength`, clip, mask, filter, prefixed attribute or `url()` paint stays, since each of those sees the path alone. A later path's first relative move becomes absolute so its points stay put. A stroke pads by its own or inherited width and miter limit, an arc's bounds use the radii it grows to, and a path holding more than 64 moves compares as one box. It is lossy because anti-aliasing can blend a pixel both paths reach differently once merged; `mergePaths` merges only `crispEdges` lines for that reason.

## JavaScript

- `syntax.js` reaches `parser` and `printer` through getters: parsing never loads the printer, and the printer loads the parser to read an asset into a `SyntaxTree`. It is the only parser: a source it refuses is refused, and terser's parse options for what is not a program (`parse.expression`, `parse.strict`, `parse.experimental_typescript`) are refused too. `toEstreeObject(node, options?)` builds the ESTree object of a node of the last parse (`SyntaxTree#estreeObject` of any tree), the same object for the same options: `ecmaVersion` (the edition whose fields it holds, the parse's by default), `ranges`, `locations` and `sourceFile`, as acorn's options of those names. A node spanning at most 1024 characters comes with its whole subtree built at once, as plain data properties; a longer one holds each child as an own accessor that reads it from the tree the first time it is read, so a long subtree nothing reads has no objects; the next parse copies the columns the objects made so far read. It bridges hooks and plugins while the parser moves to that struct-of-arrays tree. A reader the next parse must not disturb takes the tree with `takeParsedTree()` and releases it once read. The tree already reads as [the node path](#the-node-path) does, a node passed last: `type`, `start`, `end`, `range`, `name`, `value`, `field`, `fieldCount`, `flag` and `textOf` with the `NodeType`, `Field`, `Flag` and `Part` that `syntax.parser` exports. `SourceProcessor` walks the tree a parse writes as the CSS and HTML ones walk theirs, each visitor handed that path and the children taken in source order (a template's quasis and expressions in turn). Asked for `mode: "minify"`, the same walk prints: `syntax-printer.js`'s `printer` returns each node's text from its children's, as `minify` prints a source it neither compresses nor mangles, comments left out and terser's format options read from `format`. A minify walks the tree its own parse wrote (`walkSyntaxTree`) with the comments it keeps, a name printed inside its parent's text where none of its own is read: each is taken as terser's printer reaches it, by the node holding its token, and printed once the text before it is, which a text opening with it leaves to the node printing that text. What terser's stream reads off the text before a node — `has_parens` before a function or object starting a statement, `!--`, `</script` — it reads off the tree instead, the one `parsedTree()` returns while the walk runs, and through `ancestor(level)`, a node enclosing the current one; and each child's text is read once (`PrintContext#consume`), so a long one is made flat and its pieces let go as it is printed.
- `syntax-parser.js` — tokenizer, acorn-derived core and every production in one file (any parse reaches the productions). `parseProgram(input, pos, options)` is the one entry, a build's included: it writes a new `SyntaxTree`, read through `A`, and returns the program's node. `toEstreeObject` builds a node's ESTree object from the tree, leaving out the fields acorn's objects lack at the parse's edition. Beside `sourceType` (and `auto`, a module turning into a script at a top-level `return`), `ecmaVersion` and `parseError`, it takes acorn's grammar and token options, `comments` (an array to collect into) and `importPhases`. `JavascriptParser`, the concatenation, the minifier, the `SourceProcessor` and the tooling all parse through it; only a custom `parse` function replaces it. The tree path writes each node into the tree, or the one a caller passes as `syntaxTree`, as it finishes, children before their parent, an id in the tree's columns rather than an object; a key, a module name and an exported declaration are written as they are read and the checks read their names back by node, a modifier read as a key first (`get`, `set`, `async`) taken back off the tree; a function before its body ends stays an object until it is written, and an expression read as a pattern after all is retyped in place. Every edition takes a tree, each owned production checking the edition where acorn does; parser plugins do not, since acorn's own productions read their nodes back. A parse into ESTree objects keeps acorn's productions for an older edition, whose objects lack the newer fields. `regexp.js` (pattern validator) is the one on-demand piece, reached only for a pattern the host engine rejected — never `require` it from a build path.
- **Scopes:** `syntax.scopes` (`webpack.javascript.syntax.scopes`) is `ScopeAnalyzer.js`'s analysis, loaded on first use. A parse with `scopes: true`, or a `ScopeLog` it empties and refills, records names and scopes as it goes, and `analyzeScope(program)` builds the scope tree from that log in one pass. A tree with no log, such as one `fromEstreeObject` wrote, is walked instead. Call it before the next parse: it reads the tree `A` reads. Concatenation reuses one log through `JavascriptParser._parseScopes`, so a build without `optimization.concatenateModules` or `optimization.avoidEntryIife` never records.

  ```js
  const log = new scopes.ScopeLog();
  const { unresolvedReferences } = scopes.analyzeScope(
  	parser.parseProgram(code, 0, { sourceType: "module", scopes: log })
  );
  console.log(unresolvedReferences.map((ref) => ref.identifier.name));
  ```

- **`sourceType` names which production a source is**, for `parseProgram`, `process` and the printer's `minify` alike: `"module"` (the default), `"script"`, or a `FunctionBody` read as acorn's `commonjs` goal reads one (`return` and `new.target` at its top, no `import`, `export` or `import.meta`): `"commonjs"`, a CommonJS module in the function Node wraps it in, or `"event-handler"`, an event handler attribute's value in the one HTML compiles it into, which a `#!` line cannot open. HTML offers only `"event-handler"` for an attribute, never `"module"`. `minify` compresses a function's body inside a function built around its tree, so every rule a function's body reads by applies and a name it reads undeclared stays global (for a handler, the element's, form's or document's); it prints the body without that function, mapped where it was read, its `#!` line and comments kept, and a handler without the last semicolon the closing brace would leave off. `parseProgram` and `process` read import phases (`import defer`, `import source`) too.
- `syntax-specifiers.js` — the specifier scans `FileSystemInfo` reads build dependencies with: `collectCjsRequireSpecifiers` finds static `require("...")` calls, `collectEsmImportSpecifiers` an ES module's imports, re-exports and literal `import()` calls, each mapped to whether only `import()` names it. - **TypeScript:** `parseProgram(input, 0, { typescript: true })` reads TypeScript's erasable syntax and skips it, as if it were whitespace: the tree holds the JavaScript alone, at the source's offsets, as acorn would read Node.js's `module.stripTypeScriptTypes` output. A `typeRanges` array collects what was skipped, three numbers a range: start, end, and the character blanking it writes at its start (`;` before a statement, a class member or, past a line break, a `(`, `[` or template the line would run on into; `)` where a line break stands between an arrow's `)` and `=>`). `experiments.typescript` reads a `.ts`, `.mts` or `.cts` module that way in `JavascriptParser`, keeps the ranges in `buildInfo.typeScriptRanges`, and `JavascriptGenerator` blanks them (`lib/typescript/blankTypeScript.js`) in a source layer beneath the dependencies' replacements, so a replacement covering code with types in it (a dead branch) composes with the blanking. Every offset, line and column stays, so no Node.js API is needed and the source map is exact; a `module.noParse` module is parsed for its ranges when it is generated, and a custom `parse` function is handed the blanked source. Each fixture in `test/fixtures/typescript/` is parsed by `test/unitCases/typescript/node-type-stripping.unittest.js` and its tree compared with the parse of Node.js's output.
- `syntax-printer.js` — webpack's JavaScript minifier, printing, mangling and compressing in one pass; `jsMinify.js` is the `minify` the default minimizer dispatches JS to under `experiments.futureDefaults`, and goes through it alone; without that flag the minimizer dispatches to `terserMinify` as `minimizer-webpack-plugin` publishes it, running the user's own terser since webpack lists it only as a devDependency. Neither needs an option to say which, and the printer itself never loads terser. `createModules` builds what the one pass reads: the parser's tables (`createParseTables`), the mangler's names (`createFrequency`), the output stream (`MinifiedOutput`, which the node printer's stream extends), the parse into a `SyntaxTree` (`parse.parseTree`), its mangling (`mangleTree`, `mangleTreeProperties`, `mangleManglingScopes`) and the `improvements` switches the node printer reads. `prepareMinify` reads and mangles the one source a `SourceProcessor` run minifies, and `createNodePrinter`'s printer compresses it as it prints. `test/specCases/minify-corpora.spectest.js` minifies each source of each corpus in its `CORPORA` list (add a new one there) under the option sets in `OPTION_SETS` with the one `SourceProcessor` pass `jsMinify` runs and with terser, and runs each output whose test states what its input prints (terser's `expect_stdout`, swc's `expected.stdout` and `exec.rs`) in terser's sandbox: it must print that, unless `INHERITED` lists it as misprinting by an option's own contract. webpack must refuse a source where terser does and only there: where the reference refuses a source the spec allows, the parse error it answers with is listed in `REFUSED_BY_REFERENCE` with what makes the source legal, and where webpack refuses a source the reference reads, the source is listed in `REFUSED_BY_WEBPACK` with the rule it breaks (a test262 test expecting a parse error needs no entry). Summed over each corpus, webpack's outputs must gzip no bigger than terser's. An entry that stops matching fails until retired. Each output is also sized against swc's recorded one, a fixture's `output.js` or, for one of terser's cases, what swc's port of it records (gzip decides, raw breaks a tie): one bigger fails unless `test/helpers/swcSmaller.js` lists it under what swc does that webpack does not yet, and a listed one no longer bigger fails until retired. Under the default minimizer's options each source of every corpus but test262 is also minified by `oxc-minify`, held the same way to `test/helpers/oxcSmaller.js`; `test/helpers/rivalSmallerByDesign.js` adds to both lists the sources no minifier change closes (deflate's header, or swc running a transform the case's own options turn off); an oxc output that misprints is no lead. `JS_MINIFY_REPORT=<file>` tallies where webpack's is worse, the same and better. terser's corpus submodule is pinned to the `terser` devDependency — bump both together, and regenerate `data.js`.
- **Built-ins are taken as native.** The minifier assumes a program does not replace the built-ins it folds, calls without `new` or drops as pure, as oxc always and swc by default (`pristine_globals`) do; terser assumes it only under `unsafe`. It honours a write it can name: `Math.abs = f`, `globalThis.RegExp = C`, `window["Error"] = C`, `Array.prototype.join = f`. A replacement reached otherwise (an alias of the global object, a computed key, `Object.defineProperty` or `Object.assign` on it, a script's `this`, `Object.getPrototypeOf(x).m = f`) is taken as native. `compress.pristineGlobals: false` takes every built-in as possibly replaced, for a program or polyfill that patches them so.
- `yarn test:minify-corpora` — webpack's one-pass JS minifier vs the published one it replaces over every JS corpus: terser's own `test/compress` and `test/input`, test262, swc's minifier tests and oxc's; where a test states what its input prints, the output is run and must print it, webpack must refuse a source where terser does, and each corpus's outputs must gzip no bigger than terser's in total, or than its `TERSER_TOTAL_BUDGET` ratio to terser's while it still is. Each output must also be no bigger than swc's recorded one unless `SWC_SMALLER` lists why, and every output outside test262 no bigger than `oxc-minify`'s unless `OXC_SMALLER` does; `JS_MINIFY_REPORT=<file>` tallies worse, the same and better.
